## STAGE 0 — Git & Project Hygiene Setup (do this before anything else)

1. Confirm you have a git repository initialized in your main Next.js project folder. If not: `git init`.
2. Confirm `.gitignore` correctly excludes: `node_modules/`, `.env`, `.env.local`, `.next/`, `*.log`. Add any missing entries now.
3. Commit the current state as a baseline, even if messy:
   ```
   git add .
   git commit -m "chore: baseline snapshot before backend wiring begins"
   ```
4. Create a long-lived `main` branch (if not already) representing your last known-good state.
5. From now on, **every stage below gets its own feature branch** — never work directly on `main` for the rest of this roadmap. Pattern:
   ```
   git checkout -b stage/01-db-setup
   ```
6. Adopt this commit message convention going forward (keeps history readable):
   - `feat: ...` — new working feature
   - `fix: ...` — bug fix
   - `chore: ...` — config/tooling/non-functional
   - `refactor: ...` — code restructuring, no behavior change
   - `test: ...` — test additions
7. Only merge a stage branch back into `main` once that stage is fully verified working — never merge a half-finished stage.

## STAGE 1 — Database Setup (Supabase)

**Branch:** `git checkout -b stage/01-db-setup`

1. Go to supabase.com, log in, create a new project (or confirm your existing project if already created) — note the project region (pick one close to your users, e.g. Mumbai/Singapore for India).
2. Once the project is provisioned, go to **Project Settings → Database** and copy:
   - The pooled connection string (port 6543, `?pgbouncer=true`) → this becomes your `DATABASE_URL`
   - The direct connection string (port 5432) → this becomes your `DIRECT_URL`
3. Go to **Project Settings → API** and copy:
   - Project URL → `SUPABASE_URL`
   - `service_role` key (NOT the anon key) → `SUPABASE_SERVICE_ROLE_KEY` — keep this secret, never expose client-side
4. **STOP — do not inject your SQL file yet.** Per SCHEMA_AUDIT.md, your current SQL has a critical bug (`profiles.id` references the wrong table) and several other issues. Apply the fixes from SCHEMA_FIX_PROMPT.md Stage 1 through Stage 10 to your SQL/Prisma schema FIRST, in your local project, before this ever touches the real database.
5. Once your schema is fixed (per SCHEMA_FIX_PROMPT.md), run your Prisma migrations against this fresh Supabase database instead of manually pasting the raw SQL file — this ensures Prisma's migration history and the actual database stay in sync from day one:
   ```
   npx prisma migrate dev --name init
   ```
6. Verify tables were created correctly: `npx prisma studio` — browse the tables, confirm they match your schema.
7. Create your Supabase Storage buckets now (per ARCHITECTURE.md Section 6): separate private buckets for Aadhaar, PAN, Ration Card, Profile Photos. Set each to **private**.
8. Commit:
   ```
   git add .
   git commit -m "chore: database provisioned, corrected schema migrated to Supabase"
   git checkout main
   git merge stage/01-db-setup
   ```

## STAGE 3 — Better Auth Wiring (Stage 2 of PLAN.md's Phase 4, but first real backend piece)

**Branch:** `git checkout -b stage/03-auth-wiring`

1. Install Better Auth and its Prisma adapter if not already present: `npm install better-auth @better-auth/prisma-adapter`.
2. Read the Better Auth documentation for the exact server setup pattern for Next.js App Router.
3. Create/confirm `src/lib/auth.ts` — server-side Better Auth instance, configured per ARCHITECTURE.md Section 4 (email+password, 30-day session, 5-min cookie cache, custom cookie prefix, rate limiting).
4. Create/confirm `src/lib/auth-client.ts` — client-side Better Auth instance for use in Login/Register forms.
5. Create `src/app/api/auth/[...all]/route.ts` — the Better Auth handler.
6. **Remove the temporary hardcoded-credential auth scaffolding** from the previous step (the frontend-only Login/Register/Admin Login pages built earlier) — replace the fake client-side check with real `authClient.signIn.email()` / `authClient.signUp.email()` calls.
7. Implement `ensureProfile()` — a transaction that creates a `Profile` record synchronously alongside `User` creation at signup (per ARCHITECTURE.md Section 4.3 — not lazy, not a trigger).
8. Create the SINGLE shared `requireAuth()` / `requireAdmin()` utility in `src/lib/session.ts` (per AI_AGENT_RULES.md Section 3 — one definition, used everywhere, no per-file duplicates going forward).
9. Seed a single superadmin account via a script (not a registration page) — create `scripts/seed-admin.ts` or similar.

**Test with Playwright before committing:**
- Sign up a new test member → confirm real User + Profile records created in the database (check via Prisma Studio).
- Log in as that member → confirm redirect to `/dashboard`.
- Log in as the seeded admin → confirm redirect to `/admin`.
- Log out → confirm session actually terminates (check that `/dashboard` redirects to `/login` afterward).
- Test rate limiting by attempting 6+ failed logins.

10. Commit:
    ```
    git add .
    git commit -m "feat: wire real Better Auth for member and admin login/signup"
    git checkout main
    git merge stage/03-auth-wiring
    ```

## STAGE 4 — Middleware / Route Protection (proxy.ts)

**Branch:** `git checkout -b stage/04-proxy-middleware`

1. Create `proxy.ts` at the project root (Next.js 16 convention — NOT `middleware.ts`, which is deprecated).
2. Implement broad matcher patterns: `/admin/:path*` and `/dashboard/:path*` (per the earlier auth-bypass lesson — broad patterns protect future routes automatically).
3. For `/dashboard/*`: lightweight session-cookie-existence check, redirect to `/login` if absent.
4. For `/admin/*`: session check PLUS role verification (read role from session if Better Auth's `additionalFields` exposes it directly, avoiding a redundant DB query if possible), redirect to `/admin/login` if not an ADMIN.
5. Ensure NO direct Prisma/database calls happen inside `proxy.ts` itself (Edge runtime constraint) — role checks should read from the session object or a lightweight API call, not a direct DB query in the proxy file.
6. Remove the temporary client-side route-gating wrapper built in the earlier scaffolding step — this real server-side proxy replaces it entirely.

**Test with Playwright before committing (mandatory, per the standing auth re-check rule):**
- Fresh unauthenticated browser: visit `/dashboard` and every sub-route → confirm redirect to `/login`.
- Fresh unauthenticated browser: visit `/admin` and every sub-route → confirm redirect to `/admin/login`.
- Log in as member, confirm `/admin/*` is still blocked for them.
- Log in as admin, confirm both `/admin/*` and `/dashboard/*` behave correctly per their intended access.

7. Commit:
   ```
   git add .
   git commit -m "feat: implement proxy.ts with broad route protection matchers"
   git checkout main
   git merge stage/04-proxy-middleware
   ```

**Branch:** `git checkout -b stage/05-file-upload`

2. Build `/api/upload/route.ts` — server-side upload using the Supabase **service role key**, never the anon key.
3. Implement: session check → magic-byte file validation → client compression (already applied before reaching here) → server-side compression via sharp (resize max 1600px, convert to WebP, quality 75) → upload to the correct private bucket (separate buckets per document type, per SCHEMA_AUDIT.md fix) → delete old file on replacement → generate signed URL (time-limited) for display.
4. Wire the Profile page's document upload UI (built earlier in the frontend scaffolding) to actually call this real endpoint.

**Test with Playwright:**

- Attempt to upload a renamed non-image file → confirm rejection.

5. Commit:

## Rules that apply across every single stage above

- Never skip a stage's testing step to move faster — every "Test with Playwright" instruction is mandatory, not optional.
- Never combine two stages into one branch/commit — even if they feel related, keep them separate so you always have a clean rollback point.
- Never merge a branch into `main` until its stage is fully verified working.
- If a stage reveals a problem in an EARLIER stage's work, stop, fix it on its own small branch, verify, merge, THEN continue.
- Give your AI agent `ARCHITECTURE.md`, `AI_AGENT_RULES.md`, `PLAN.md`, and this `MASTER_BUILD_ROADMAP.md` at the start of every session, and tell it explicitly which numbered stage you're on — never let it jump ahead.
